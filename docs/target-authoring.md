# What writing a target actually costs

Notes taken while describing three systems, kept so `shoal init` is built from
evidence rather than from a guess about what a target needs. The first version
of Shoal was built from a guess about exactly that, and a second target found
six things wrong with it.

The three: a furniture back office, an agency portal, a storefront. All
Fastify + Prisma + Postgres + Zod, which is the case worth automating first.

## Every step, and who has to do it

**Mechanical** — derivable from files that already exist, no judgment.
**Semi** — derivable, but needs one read of a handler to confirm a shape.
**Judgment** — a person who understands the business.

| Step | Kind | Source | Got it wrong |
|---|---|---|---|
| Stack, entry point, port, database | Mechanical | `package.json`, `.env` | — |
| Health path | Mechanical | grep route registrations | **once** — assumed `/api/health`, the third was `/health` |
| Login path | Mechanical | auth route file | — |
| Login response shape | Semi | must read the controller's return | **once** — assumed `{ token }`, the second was `{ success, data: { token } }` |
| Credentials | Judgment | seed file, env fallbacks | non-admin passwords were simply unknowable on two of three |
| Route table | Mechanical | `register(routes, { prefix })` + route files | — |
| Request payloads | Mechanical | Zod schemas | — |
| Tables and columns | Mechanical | `information_schema` | — |
| Rate limits | Mechanical | grep `rateLimit` in route config | **twice** — discovered by being throttled, not by looking |
| Role enum | Mechanical | Prisma enum | — |
| Which routes each role may reach | Semi | read the guard | **once** — assumed one page per route; the guard took a list |
| World collections | Semi | what create endpoints return | — |
| Which actions matter, and their weights | Judgment | — | — |
| `collidable` vs `collideVariants` | Judgment | — | this is where the bugs are |
| Outbound channels to blank | Judgment | — | safety-critical; nothing derives it |
| `requiresWorld` | Judgment | — | — |
| **Soundings** | **Judgment** | — | the entire product |

Roughly: the mechanical and semi-mechanical steps were about **two thirds of
the wall clock** and produced almost none of the value. Every one of the five
mistakes above was in that two thirds. None was in the soundings.

That is the case for `shoal init` in one paragraph. It is not that generation
saves typing — it is that the boring parts are where I made every error, and a
generator does not mistype a health path.

## What `shoal init <path>` should produce

A draft that boots, logs in, surveys, and runs the structural soundings — with
every judgment call marked and left undone.

**Derived outright:**

- `root`, `entry`, `port`, `sourceDb` from `package.json` and `.env`
- `healthPath` by grepping registered routes for a health-shaped one
- `auth.path` from the auth route; `auth.token` by reading the login return
- `env` overrides for every key in `.env` matching a channel pattern
  (`*_API_KEY`, `*_SECRET`, `*_TOKEN`), blanked — safe default, since a
  simulated customer must never reach a real one
- a suggested `--pace` computed from the *lowest* `rateLimit` on any route the
  actions touch. Getting this wrong wasted two voyages
- `world` collections, one per model returned by a create endpoint
- one `httpAction` per mutating route, payload shape lifted from its Zod
  schema, `weight: 1`, `collidable` off, each marked `TODO: weight, contention`
- `personas`, one per role in the enum, with `email` blank and a `TODO`
- structural soundings wired up: `pagingIsStable` and `listingMatchesCount`
  against every paged list endpoint found

**Proposed, not decided** — written into the draft as commented candidates:

- **Cached-aggregate columns.** A numeric column on a parent whose name looks
  like a running figure (`paid*`, `*Count`, `total*`, `*Amount`) beside a child
  table with a foreign key to it. Three systems, three instances, three
  different names — and in all three the hand-written version of this check was
  the one that found real money missing. Propose a
  `cachedAggregateMatchesRows` for each and let a person confirm it.
- **Arithmetic columns.** A parent with `subtotal`, a discount, a tax and a
  total is proposing its own equation.
- **Non-negative columns.** Anything called `stock`, `quantity`, `balance`.
- **Unique-under-concurrency columns.** Any `@unique` string column written
  during a create — an order number, an invoice number. In the storefront this
  is generated by read-max-then-increment and collides under load; in the
  furniture system the same thing is done with a sequence row and does not.

**Never generated:** the `because` on any sounding. A generated one would be
written from the schema, which is the implementation, which is the one thing a
sounding must not be derived from. Leave it blank and refuse to run until it is
filled in.

## Measured: what the scaffolder actually saved

`shoal init` was then run against a fourth system nobody had described — a food
delivery kitchen — and the draft finished by hand.

**Read correctly, first time, with no help:** entry point, database name, health
path, the login path *with its prefix applied*, all three roles, 158 routes of
which 18 were drafted as action stubs with correct methods and paths, 29 tables,
10 outbound keys to blank, and 12 candidate soundings ranked so the 4 worth
reading came first.

**Wrong, and each one now fixed in the generator:** the login path was emitted
without its prefix; the world type came out with a lowercase name so the draft
did not compile; every foreign key became a cached-aggregate candidate, most of
them nonsense; and the rate limit was missed entirely because it is registered
app-wide rather than per route — which cost a voyage that came back 58%
throttled.

**Left to a person, as intended:** which actions matter, what contends with
what, the survey, and every `because`. That was the whole of the remaining
work, and it is the whole of the value.

Two more engine gaps surfaced doing it: a system can seed different passwords
for different roles, which one target-wide password could not express; and two
of four systems wrap the login reply as `{ success, data: { token } }`, which is
common enough that the default now probes for it rather than making the first
voyage fail.

## What four targets taught the engine

Recorded because each was invisible from the target before it:

| Found by | Was welded to target one |
|---|---|
| Target 2 | login shape, health path, `role === 'MANAGER'`, one login per session, no rate-limit handling, `body.error` only |
| Target 2 | a failed boot leaked the process; a target could not set the booted environment |
| Target 3 | every persona had to authenticate — a public checkout could not be modelled at all |
| Target 3 | starvation only fired at zero success, so an action succeeding one time in four printed as "nothing tripped" |
| Target 4 | one password per target; the login envelope; an action attempted ZERO times was invisible to both the starvation and degradation checks |

The pattern is the same one every time: the engine could not tell the
difference between "this held up" and "this was never tested". A storefront
whose checkout failed three times in four read as a clean voyage. An action the
swarm never once attempted read as a clean voyage. Both are now reported above
the verdict, alongside throttling, because a summary that only counts
violations is confident about exactly the things it did not measure.
